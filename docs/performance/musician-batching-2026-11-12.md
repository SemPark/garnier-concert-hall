# 연주자 배칭 CPU 최적화 — 2026-11-12

실제 적용은 **포즈가 바뀌지 않은 연주자의 부품 검사 생략**이다. 인스턴스 부분 갱신은 실험 후 CPU 비용이 증가해 되돌렸다. 그래픽, 애니메이션, 해상도, LOD 기준, 갱신 주기는 변경하지 않았다. 기존 미커밋 5개 파일의 diff는 작업 전과 동일하며, push/배포는 하지 않았다.

## 확인한 병목과 변경

- `World.ts`는 이미 30Hz/20Hz 포즈 갱신과 가시성 검사를 수행하고 `poseAt`을 기록한다.
- `batching.ts`도 기존 `posed` 캐시로 월드 행렬 순회를 생략하지만, 이어지는 재질별 루프는 모든 움직이는 부품의 행렬/모프를 검사했다. 클래식에서는 배칭 호출당 2,461개 행렬 비교가 남았다.
- 기존 `posed` 판정 결과를 작은 `ActorPose.dirty` 상태로 공유한다. 별도 포즈 타이머나 애니메이션 버전은 만들지 않았다.
- 재질별 부품 배열은 원래 연주자 순서로 연속되어 있다. 초기 구성 시 그 구간의 끝만 저장하고, 카메라/가시성 재사용이 가능하며 포즈가 그대로이면 구간 전체를 건너뛴다.
- 카메라 이동/회전/투영/지휘 상태 변경 때는 기존 `actorView`와 LOD/가시성 검사를 그대로 수행한다. 이때도 포즈가 유지되면 행렬 비교와 불필요한 복사는 생략한다.
- `poseAt`이 없는 동적 대상은 종전과 같이 검사한다. `Avatar.ts`, `World.ts`에 새 수정은 없다.

## 비교 방법과 한계

Apple M4 / Ego Chromium에서 실제 `buildOrchestra`와 `Avatar.update`를 사용한 결정적 재생이다. 클래식 65명, 재즈 17명. 기존 배칭 소스와 최종 소스를 같은 브라우저/포즈/카메라로 비교했다. 버전 순서를 번갈아 3회 측정, 회당 240회 워밍업 후 480회의 평균이다. 계수용 monkey patch는 시간 측정과 분리했다.

아래 수치는 **연주자 재생 테스트의 배칭 호출당 CPU 시간**이며 공연장 전체 프레임 시간이 아니다. 애니메이션 시간에는 재생 도구의 카메라/가시성 준비도 포함된다. 정지 조건은 `poseAt`이 유지되는 경로를 따로 검사하는 합성 조건이고, 실제 음악 중 정지 시간의 비중을 의미하지 않는다. 지휘 조건은 지휘자의 표시 전환과 포즈 변경을 재생하며 실제 사용자 탭 전체를 자동 조작한 E2E 테스트는 아니다.

iPhone 13 Pro 실측은 하지 않았다. 과거 약 28ms와 하드웨어/장면 조건이 달라 직접 비교할 수 없다. 브라우저 앱 전체를 이용한 초기 측정은 불안정해 기준값으로 사용하지 않았다. GPU 비교는 워밍업한 별도 연주자 장면에서 수행했다.

| 조건 | 변경 전 배칭(ms) | 변경 후(ms) | 감소율 | 애니메이션 전→후(ms) |
|---|---:|---:|---:|---:|
| 포즈 유지 | 0.255 | 0.060 | 76.7% | 0.005→0.004 |
| 먼 시점 연주 | 0.926 | 0.870 | 6.1% | 0.199→0.197 |
| 가까운 시점 연주 | 0.924 | 0.871 | 5.8% | 0.200→0.194 |
| 카메라 이동·회전·화면비 변경 | 1.011 | 0.952 | 5.9% | 0.180→0.178 |
| 지휘 상태/포즈 전환 | 0.950 | 0.902 | 5.1% | 0.204→0.202 |

애니메이션은 수정하지 않았으므로 그 시간 차이는 성능 개선으로 주장하지 않는다.

### 비교·기록·업로드

클래식 420회 재생 합계(초기 120회 포함):

| 조건 | 행렬 비교 전→후 | 인스턴스 행렬 기록 전→후 |
|---|---:|---:|
| 포즈 유지 | 1,033,620→2,461 | 2,913→2,913 |
| 먼 시점 연주 | 1,033,620→688,560 | 1,008,100→1,008,100 |
| 가까운 시점 연주 | 1,033,620→688,560 | 1,007,646→1,007,646 |
| 카메라 이동 | 1,033,620→604,199 | 882,772→882,772 |
| 지휘 상태 | 1,033,620→688,560 | 997,756→997,756 |

최종안은 슬롯/업로드 구조를 유지한다. 실제 WebGL `bufferSubData` 계수(69회 렌더): 일반 연주 **3,243회 / 10,587,072바이트**, 지휘 조건 **3,105회 / 10,454,592바이트**, 모두 전후 동일. 일반 연주 75 draw calls, 지휘 상태 73으로 전후 동일. 부분 범위를 적용하지 않았으므로 업로드 범위도 기존과 같다.

별도 960×480 연주자 장면 120프레임: **29.30→29.07 FPS**, 75 calls. FPS 향상은 확인되지 않았다. 배칭에서 절약한 약 0.05~0.06ms만으로 전체 렌더링 속도가 크게 달라질 정도는 아니다. 이 수치를 공연장 전체나 모바일 FPS로 해석하지 않는다.

## 부분 갱신을 남기지 않은 이유

안정된 인스턴스 슬롯을 저장하고, 바뀐 행렬/모프만 다시 기록하며 버퍼당 하나의 포함 범위로 업로드하는 두 가지 구현을 시험했다. 가시성/LOD 변화에는 전체 압축 슬롯을 재구성하고 색상·모프를 함께 정렬했다.

클래식 먼 시점 420회에서 행렬 기록은 1,008,100→688,316으로 약 31.7% 감소했다. 그러나 브라우저의 먼 시점 배칭은 약 0.832→0.883ms, 이동은 1.020→1.063ms, 지휘는 0.953→0.997ms로 느려졌다. 원인은 다수 부품이 동시에 움직이는 상황에서 dirty 목록·슬롯·범위 관리가 절약한 복사보다 비쌌기 때문이다. 부분 갱신의 실제 GPU 시간 개선은 입증하지 못했다. 최종 코드에는 남기지 않았다.

## 회귀 검증

- 클래식/재즈 각각 5개 조건 × 420회에 대해 표시 상태, 인스턴스 순서·행렬·색상·모프 데이터 SHA-256이 원본과 동일.
- 실제 WebGL 캡처: 클래식 원거리/근거리/이동/지휘, 세로 화면비, 재즈 근거리의 원본·최종 이미지 픽셀 차이 **0**. 별도 연주자 장면 검사이며 공연장 전체 모든 시점의 시각 검증을 대체하지 않는다.
- 신규 테스트: 동일 포즈 비교 생략, 카메라 회전 후 복귀, 눈 깜빡임만 변경, 지휘자 가시성 변경 시 슬롯·색상·표정 일치, 근거리/원거리 LOD 복원.
- `npm test`: 141/141 통과. 기존 좌석/지휘/손/캐릭터 동작 테스트 포함.
- `npm run check`, `npm run build`, `git diff --check` 통과. 기존 번들 크기 경고는 남아 있다.

## 파일 및 재현

실제 제품 코드 변경은 `src/scene/batching.ts`뿐이다. `tests/batching.test.ts`와 개발 전용 `scripts/benchmark-musicians.ts`, `scripts/musician-replay.ts`, `scripts/batching-benchmark.html`을 추가/갱신했다. 후자는 앱 진입점에서 import하지 않아 배포 번들에 들어가지 않는다.

```sh
# 비교용 임시 원본. 측정 후 반드시 제거한다.
git show 248d0f5:src/scene/batching.ts > src/scene/.batching-baseline.ts
node --import tsx scripts/benchmark-musicians.ts baseline classic
node --import tsx scripts/benchmark-musicians.ts current classic
node --import tsx scripts/benchmark-musicians.ts baseline jazz
node --import tsx scripts/benchmark-musicians.ts current jazz
# 로컬 Vite: /scripts/batching-benchmark.html (재즈는 ?hall=jazz)
# window.replay.prepare(name, kind), measure(name, kind), frame(name, kind, frame)
# name: baseline/current, kind: idle/far/near/moving/conducting
rm src/scene/.batching-baseline.ts
```

원시 측정값은 같은 폴더의 `musician-batching-2026-11-12.json`에 있다. 다음 단계는 실제 iPhone의 동일 장면 측정이다. 움직이는 연주자의 월드 행렬 계산과 전체 그룹 업로드, 공연장 렌더링 비용은 남아 있으며 별도 프로파일링이 필요하다.
